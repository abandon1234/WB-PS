### 关键技术决策

**1. 掩膜生成改用「局部背景差分」而非全局阈值**
原先用 Otsu + 全局 bg_level 做 soft mask，在渐变/纹理背景上会把整片背景
误判为文字（ROI 内 mask 面积爆炸到 17 万 px）。
改为形态学估计局部背景图：暗文字用 `close - gray`，亮文字用 `gray - opened`。
**必须只取一个方向**——取两者 max 时，开运算会把笔画间的细窄背景条整片掏空，
使 noise 分位被顶到 223、阈值失效。

**2. 颜色统一为 RGB，BGR 只在像素级操作内部转换**
`_dominant_color` 返回 RGB；eraser 里填充前反转成 BGR。
最初没统一，前端和 PIL 把 BGR 当 RGB 用，颜色全错。

**3. 字号由「墨迹高度 ÷ 实测字面比」反推**
实测值：微软雅黑汉字 0.908、黑体 0.883、宋体 0.896、DengXian 0.871；
Arial 大写 0.717、Times 大写 0.663。先验系数从 0.86 修正为 0.90 后，
字号误差从 41% 降到 4.4%。

**4. 擦除用途必须关闭连通域去噪**
`_text_mask(denoise=False)`。文字顶/底部的抗锯齿碎片常是面积 <26px 的
孤立连通域，被当噪点剔除后会在擦除结果里留下一圈淡轮廓
（肉眼几乎看不出，但像素差异 200+）。

**5. 擦除外扩参考区按「框高」算，不按长边**
`pad = clip(0.9 * h, 8, 48)`。按长边算会让 ROI 吞掉相邻行，污染掩膜。

**6. 分级擦除 + 残留自检**
solid→fill / gradient→linear / texture→inpaint；
擦完自检（框内边缘能量 ÷ 周边背景），偏高就加大 grow 重擦，最多三轮。

**7. 字号自适应加下限**
缩放比 <0.6 时不缩放（保持字号 + 提示），否则新文字明显比周围小、一眼看出被改。

## 修复：loading 遮罩关不掉，一直转圈（用户反馈）

**现象**：识别早已完成（状态栏"识别完成 · 26 处文字"、列表已渲染），
但画布上的「正在识别文字…」转圈遮罩不消失；实际从打开页面起就一直显示。

**根因**：CSS 优先级陷阱。
`.loading { display: grid }` 是作者样式，优先级高于浏览器默认的
`[hidden] { display: none }`（UA 样式），
所以 `$('loading').hidden = true` 完全无效。`.empty`（空状态）同病。

**佐证**：遮罩上的文案是「正在识别文字…」——正是 `busy(false)` 里
默认参数写回的文案，说明 hidden 被设置了、只是不生效。

**修复（双保险）**：
1. CSS 加 `[hidden] { display: none !important; }`
2. JS 新增 `show(el, on)`：同时写 `el.hidden` 和 `el.style.display`，
   不依赖 CSS 优先级；所有 `.hidden = x` 调用点改为 `show(el, x)`；
   `init()` 里显式重置各层初始可见性
3. HTML 资源加 `?v=1.1` 查询串，避免旧 CSS/JS 被浏览器缓存

**教训**：任何"作者样式声明了 display"的组件，都不要只靠 `element.hidden`
控制显隐。这是通用陷阱，不只是本项目。

## 优化：把 -500 改成 -700 后改动痕迹明显（用户反馈）

**现象**：数字替换后一眼能看出被改过 —— 新字明显偏细、字形不同。

**三个根因**（都不是"文本框限制"）：

1. **字重只有布尔判断**。原来 `bold = stroke_ratio >= 0.135`，
   没有 medium/semibold 中间档，原图是 medium 时一律渲染成 regular → 偏细。
   且实测发现 `stroke_ratio` 本身噪声大（同为 regular 的样本分布在 0.065~0.111），
   单靠它分类不可靠。

2. **字体族是"按语言推荐"而非"按字形匹配"**。纯数字文本直接给 Arial，
   而原图可能是 Verdana / Segoe UI / 等宽体，宽高比差 6%~15%，一眼看出。

3. **匹配逻辑本身有缺陷**（第一版改进后暴露）：
   - 候选池用了系统全部 234 个字体，会选中 ITC Bookman、ITC Avant Garde Gothic
     这类"比例接近但字形完全无关"的冷门字体
   - 只用宽高比一个特征，区分不了 Segoe UI vs Trebuchet MS、Helvetica vs Calibri
     （得分几乎打平）
   - 没过滤"渲染不出该文本"的字体 → 字形匹配给**中文**选中了 Calibri，
     墨迹度量整体失真，字号被算成 1.7 倍（渲染探针从 47px 变 78px）

**最终方案**：

- `_stroke_width` 改成距离变换 + 面积/周长双法交叉（细笔画时偏向面积法）
- 新增 `weight_class()` 输出 light/regular/medium/bold/black 档位
- **笔画闭环校准**：渲染 → 用与测量原图**相同口径**测渲染笔画宽 → 补描边 →
  再测，最多两轮；原图更细则尝试切同族 Light/Thin 变体
- **两阶段字体匹配**：
  1. 宽高比 + 墨迹填充率 + 笔画比，从**常用字体白名单**筛出 shortlist
  2. 用**原文字的真实墨迹轮廓** vs 候选渲染轮廓做形状 IoU 决出最佳
     （必须用原文字，那才是图里真实存在的可比形状）
- `_font_supports()` 用 `font.getmask()` 判断字形是否存在
  （无墨迹 或 与私有区 \uF8FF 渲染一致 → 不支持）

**验证**（`tools/font_match_test.py`，用已知字体画 "-500.00" 再改成 "-700.00"，
与"同字体直写 -700.00"的参考图比形状 IoU）：

| 阶段 | 字体命中 | 平均形状 IoU |
|---|---|---|
| 初始（仅按语言推荐） | 2/9 | 0.627 |
| 仅宽高比 + 全量候选 | 4/9 | 0.690 |
| 多特征 + 白名单 | 4/9 | 0.690 |
| **两阶段（白名单 + 形状 IoU）** | **8/9** | **0.779** |

笔画校准：目标 5.1px / 实际渲染 5.1~5.5px（误差 < 0.4px）。

**排查中的两个坑**（避免以后重复踩）：

- 可视化对比图里曾以为"Verdana 字距过大、Consolas 字符重叠"，
  实为拼接脚本按各自宽高比缩放导致的**视觉误导**。
  正确做法：固定画布尺寸等比缩放居中（`norm_mask` 已修正）。
  另用原生 PIL 渲染做对照，验证逐字符布局与原生的宽高比差 < 1%。
- `_text_mask` 的 tight/denoise 开关语义：**度量用 tight+denoise，
  擦除用 loose+不去噪**，反过来都会出问题。

## 功能：自定义字体目录

**需求**：除了系统字体，也要能用自己的字体做替换。

**实现**：

- 项目根新增 `fonts/` 目录（含 README 说明），在 `app/fonts.py` 里作为
  `_font_dirs()` 的**第一优先级**，同名族优先用用户的版本
- 磁盘缓存改为指纹化：`{"_fingerprint": [[dir, mtime], ...], "_fonts": {...}}`。
  目录 mtime 在文件增删时会变，因此**加/删字体后缓存自动失效**，
  不需要手动清 `.font_cache.json`，也不会出现"放了字体却不生效"
- 接口：`GET /api/fonts/user`、`POST /api/fonts/upload`（multipart 多文件）、
  `DELETE /api/fonts/user/{name}`、`POST /api/fonts/reload`
- 上传安全：扩展名白名单（ttf/otf/ttc/otc）、文件名正则清洗防路径穿越、
  64MB 上限、**落盘后立刻用 PIL 解析校验**，解析失败就删掉不留垃圾文件；
  重名自动加序号不覆盖
- 删除时用 `os.path.dirname(target) == 字体目录` 二次校验，杜绝穿越
- 前端：字体下拉首项「自动匹配」，自定义字体带 `★` 前缀；
  字体下方加「导入字体 / 重新扫描」两个按钮和已导入数量

**注意点**：

- `fonts/` 目录名与 `app/fonts.py` 模块同名。因为代码里全是
  `from . import fonts` / `from app import fonts` 相对/包内导入，
  不会与项目根的 `fonts/` 目录冲突（裸 `import fonts` 才会有歧义）。
- `.gitignore` 用 `fonts/*` + `!fonts/README.md`，保留目录与说明，
  但不把字体文件提交出去（很多人用的是有版权的商业字体）

**验证**：`tools/api_test.py` 新增第 7 节，覆盖上传 → 落盘 → 进入字体库 →
删除 → 文件移除 → 非法格式拒绝，全部通过（33/33）。

## 修复：文本框把字号"限住"，900 改 1400 后字明显变小（用户反馈）

**现象**：`-900.00` 改成 `-1400.00`，新数字肉眼可见比原数字小。

**根因（比表面严重得多）**：宽度比较用错了基准。

`render()` 里判断"是否过宽"时用的是 `content_size()` 返回的**图层画布宽度**，
而 `_draw_text_layer` 生成的图层左右各带 `pad ≈ 0.35 × size` 的透明 padding。
于是 `cw ≈ 墨迹宽 + 0.7 × 字号`，比原墨迹宽凭空多出几十像素，
`cw > target_w * 1.15` **几乎每次都会命中**。

实测佐证：把 `-900.00` 原样写回 `-900.00`（内容完全没变），
字号也从 74 被压到 67、`fitted=True`。也就是说**任何替换都会触发缩字号**。

**修复**：

1. 新增 `layout()` 取代 `content_size()`，用 **`_content_bbox()` 的墨迹 bbox**
   计算总墨迹宽高和各行原点。宽度比较、对齐、定位全部改用它。
2. 定位也顺带修正：图层原点 = 墨迹目标位置 − 墨迹在图层内的偏移
   （`draw_x = row_left - bbox[0]`），消除了 padding 造成的整体偏移。
   副作用是形状 IoU 从 0.779 微升到 0.787。
3. **策略调整**：`auto_fit` 默认改为 **False**。默认只在溢出超过
   `HARD_OVERFLOW=1.8` 倍时才收敛，且下限 `FIT_FLOOR=0.72`；
   1.08~1.8 倍之间保持原字号并提示。理由：字变小比"略超出原位置"更显眼，
   而实际场景里文字旁边多半是空白。
   `pipeline._edit_params` 的默认值同步改为 False，
   `_dirty()` 的开关判断改为「与默认值不同才重绘」（因为默认值反转了）。

**修复后实测**（原文字 `-900.00`，字号 74，墨迹 239×53）：

| 新文字 | 字号 | 缩放 | 墨迹高/原 |
|---|---|---|---|
| `-900.00` | 74 | 否 | 1.02 |
| `-1000.00` | 74 | 否 | 1.02 |
| `-1400.00` | 74 | 否 | 1.02 |
| `-9000.00` | 74 | 否 | 1.02 |
| `-900.000000` | 74 | 否 | 1.02 |
| `-123456789012` | 61 | 是（溢出 116%） | 0.83 |

**通用教训**：任何"测量尺寸后做阈值判断"的地方，都要确认**测量口径一致**。
这里是"图层画布 vs 墨迹 bbox"；同类坑还有之前的
"距离变换 vs 面积/周长"（笔画宽度）、"tight vs loose 掩膜"（墨迹几何）。

## 修复：改文字后整行上移 20px + 改成底部基线对齐（用户反馈）

**现象**：`-1000.00` 改成 `-1400.00` 后，文字整体往上跑了一截。
用户明确指出期望："一般文本框的底下那条线为基准"。

**量化**：只要文字内容变化（哪怕 `-1000.00` → `-1000`），**Δtop 恒为 -20px**。
字高只差 1px，所以不是居中算错，是一处固定偏移。

**根因（两个 bug 叠加在 `_content_bbox` / `layout`）**：

1. `_content_bbox()` 用 `layer.getchannel("A").getbbox()`，即 **alpha 非零**。
   LANCZOS 缩放会在字形轮廓外围留下极低 alpha 的振铃伪影（1~20 量级），
   `getbbox()` 把这些也算作内容 → 实测墨迹高度被算成 **96**，真实只有 **54**。
2. `layout()` 里高度算成了 `upper + lower`，应为 `lower - upper`。

两者叠加使 `ink_h` 虚高，而定位是
`ink_top = target_y + (target_h_ref - ink_h)/2`，
于是 `84 + (53-96)/2 ≈ 62`，正好上移 21px —— 与实测 -20 吻合。

**修复**：

- `_content_bbox` 改用 **alpha > 32** 阈值，并统一返回 `(x, y, w, h)`
  （原来是 PIL 的 `(left, upper, right, lower)`，调用处混用两种语义，
  正是 bug 2 的来源）
- `layout()` 的高度计算与合成处的 `row_w` 同步改用新格式
- 新增 **`valign`（bottom | center | top）**，**默认 bottom**：
  按底部（无降部即基线）对齐。阅读时视觉锚点是基线，
  居中则会在新旧墨迹高度不同时把整行推走。
  `pipeline._edit_params` 与 `_dirty()` 同步支持，前端加了三段选择器。

**修复后实测**（1000 → ABC，故意让新旧字高不同）：

| valign | Δtop | Δbottom | 含义 |
|---|---|---|---|
| **bottom** | -2 | **0** | 基线不动（默认）✔ |
| center | -1 | +1 | 中心不动 |
| top | 0 | +2 | 顶部不动 |

数字替换（等高）时三种都收敛到 ±1px（二值化误差）。

**副作用**：形状 IoU 从 0.787 升到 **0.803**（历史最好），说明底部对齐本身也更贴合原图。

**又一次印证同一条教训**：测量口径必须统一。
这次是"`getbbox()` 的非零语义 vs 实际墨迹范围"，
以及"`(l,t,r,b)` vs `(x,y,w,h)` 两种 bbox 语义混用"。

## 建立版本备份（用户要求"将这个版本备份"）

**背景**：项目原本不是 git 仓库。

**采用双保险**：

1. **Git 版本管理**（管演进：可 diff、可回滚）
   - `git init`，身份只写在仓库局部配置（`user.name=杨世旺`），不污染全局
   - 首个发布点 tag `v1.0.0`，4 个提交，工作区干净
   - **坑**：项目里没有 git 在 PATH 上。PortableGit 的可执行文件在
     `~/.workbuddy/binaries/PortableGit/versions/1.2.0/cmd/git.exe`
     （注意是 `cmd/` 不是 `bin/`，`bin/` 下只有 bash 相关）
   - 加了 `core.quotepath=false` 让中文文件名正常显示，
     `i18n.commitEncoding=utf-8` 保证中文提交信息不乱码

2. **快照脚本** `tools/snapshot.py`（管留档：完整离线副本）
   - 版本号自动取当前 git tag，工作区脏时加 `-dirty` 后缀

     （避免分发有版权的商业字体），但备份时应该带上
   - 输出到项目上一级，形如 `WB-PS-v1.0.0-20260925-1039.zip`
