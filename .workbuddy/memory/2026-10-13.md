## 新功能方向分析（未定案，待用户选）

用户问：除生图外，还能做哪些日常/工作场景的功能。已联网核过需求，结论与候选池如下。

**战略判断**：核心资产不是生图，而是「搜索-检测 → 识别 → 风格分析 → 原位擦除 → 原样式重绘」

新功能应沿这条管线外扩，不要新开品类。

**联网核到的市场信号**：

- 图片翻译（保留排版）已是付费品类（TranslateImage / Transpic / AI Image Translator，
  约 $9.9/月），其官方卖点写的「文字移除要完美保留背景」「保留字体与排版」
  = 本项目的 erase + style + render。

  但**只有手机 App，Web 端是空位**。
- 图片转 Excel：市场大（Lido 9.4/10，企业版 $499/mo），免费工具通病 = 要上传 + 带水印 + 复杂表格失真。
- 趋势：2026 浏览器本地 AI 已成品类，业内点名「混合管线：轻任务本地跑、重任务走云端」= 本项目现有架构。

**候选池（按复用度分层）**

- T0 复用现有管线：图片翻译·原位换字 / 批量改字 / 本机打码脱敏 / 截图取文字
- T1 加轻模型或纯算法：截图转表格 xlsx、证件照制作、去背景抠图、图片批处理、二维码条码、批量水印
- T2 需新模型或云端：老照片修复超分、文档转 Markdown、手写体识别、云端团队素材库、短链分享

1. 现装的是 `ch_PP-OCRv3`（中英），图片翻译需换多语言识别模型，这步不是零成本。

4. 截图转表格赢在准确率（合并单元格 / 复杂表头），别急着铺功能。
5. 证件照只做换底与规格排版，不碰换脸 / 身份证。

## 第 1 期已实施：取文字（能真用了）

识别 9 行全中、耗时约 1.2s（模型已缓存时）。

**新增 `web/engine/extract.js`** —— 纯函数层，四项职责：

- `buildLines`：分行 + 排序。按框中心 y 升序，与当前行中心差 ≤ **行高中位数 × 0.6**
  归为同一行；行内按 x 升序。高度量级差 > 2.6 倍的不并（大标题紧挨的小字是两行）。
  这是**第二次兜底**（`mergeLines` 已按 0.45 倍容差合过一次），所以容差取得略宽。
- `groupParagraphs`：相邻两行**四条全中**才并段 —— 左边界差 < 行高中位数 × 0.5、
  行距 ∈ (-0.6, 1.6) 倍行高、**行高比 ≥ 0.62**、上一行末尾不是句末标点。
  第 3 条是实测补的：没有它，「大标题」会并进下面的正文。
- `toPlainText`：段间空行、段内保留换行（行结构对逐行核对有用）。
- `toMarkdown`：段内多行合一行（OCR 换行是排版换行不是语义换行），
  整段像列表项时保留逐行；标题层级按**行高**推（≥ 中位行高 × 1.4 → `##`，
  × 1.2 → `###`）—— 取文字不跑样式分析、拿不到 `style.font_size`，行高是等价代理。
- `joinSegments(texts, {gaps, lineH})`：两侧都是 ASCII 词字符才补空格；
  **两片间隙 ≤ 行高 × 0.34 时不加空格**（那是同一个词被 OCR 切碎了，
  「SN-2026-0918-A7」按纯文本规则会插出一串空格）。

**`web/engine/localapi.js` 新增 `/api/text/detect` 通道**（`textDetect`）：
只跑 `detect()`，**省掉 `analyzeMany`**（样式分析要逐框裁图扫背景跑模板匹配，偏贵），

悬停双向高亮、点框滚到行。导出走 Blob + `<a download>`；复制有 clipboard 兜底

## 取文字：长图默认「适应窗口」（用户反馈「显示太大了」）

用户截图反馈：618×2560 的长截图在取文字左图里被按宽度铺满，拉到两千多 px 高，
得一路滚、右侧文本也被挤没意义。

**根因**：`.tw-imgbox{max-width:100%}` + `img{max-width:100%}` → 图被按画布宽度铺开。

**改法**：默认等比收进可视区，另给一组缩放控件（`适应 / − / 比例 / +`，点比例回 100%）。

- `web/text.css`：`.tw-imgbox` **去掉 max-width**（保留就会把长图按宽度铺开，
  而里面的 overlay 是 `inset:0` + 百分比定位，会跟着被压扁、坐标对不上）。
  图的实际显示尺寸由 JS 直接写在 `img` 上，imgbox 缩到内容大小 → 框永远贴合。
  新增 `.tw-zoom / .tw-zbtn / .tw-zval / .tw-stage-btns`。
- `web/text.js`：`fitScale()` = `min(可视区宽/原宽, 可视区高/原高, 1)`（**不放大**，
  小图保持原始像素）；`applyImageScale(k)` 写 px 尺寸 + 更新比例读数；
  `ResizeObserver` 只在 `zoomMode==='fit'` 时跟随（手动定过就不动）。
  `canvasBox()` 量不出尺寸（视图隐藏 → 0×0）时返回 null，调用方跳过 ——
  切回视图时 RO 会再触发一次，自动补上适应。
  **`ZOOM_STEP = 1.15` 感知阈值**：适应比例常恰好贴着某个挡位（24.7% vs 25%），
  没有它第一下 + 只是从 25% 挪到 25%，像点了没反应。加阈值后 25% → 33%。
- `showImage` 先把 img 设 `visibility:hidden`，等 `load` 里适应算好再亮 ——
  否则会闪一下原尺寸的大图。
- `web/index.html`：舞台头部加缩放控件；`?v=` 3.8 → **3.9**。
- `tools/probe_views.mjs` 新增 **[2f]**：在页面里现造 618×2560 长图（把样例图纵向拼 5 份）
  走真实 file input 路径，断言「不超可视区 / 长边接近铺满 / 默认非 100% / + 明显放大 /
  放大后框不跑偏 / 点比例回 100% / 点适应收回」。**断言 48 → 56，全绿。**
- 坑：`[2c]` 结束在「打码」页签，取文字面板是隐藏的（量出来 0×0）——
  `[2e]` 开头要先切回「取文字」页签再喂图，否则所有布局断言都拿不到真实尺寸。

用 618×2560 的合成长图实拍确认：适应窗口时 152×633（25%，整张收进可视区）、
点比例 → 618×2560（1:1，可纵向滚动），检测框在两种比例下都严丝合缝。
