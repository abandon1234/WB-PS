# 「文字工坊」第一版实施方案

> 定位：**先自己用顺手，顺手留出做成产品的口子。**  
> 本方案只覆盖图像文字类新功能，不涉及生图。  
> 编写日期：2026-10-13

---

## 1. 核心判断：一个前半段，三种输出

现有引擎里，`web/engine/index.js` 已经把「图片里的文字」这件事拆得很干净：

- `detect(cv, ocr, imageBgr, {...})` → 文字框 + 文本 + 置信度（不含样式，较快）
- `analyze(cv, ocr, fonts, imageBgr, {...})` → 在 detect 之上补样式分析（字体/颜色/描边/字号）
- `applyEdits(cv, fonts, imageBgr, items, edits)` → 按 edit 重绘
- `previewItem(...)` / `eraseAll(...)` → 单框预览与擦除

要做的三个新功能，**前半段完全一样，差别只在"后半段输出什么"**：

| 功能   | 用哪个前半段               | 后半段（新增）                                   | 是否需要重绘   |
| ---- | -------------------- | ----------------------------------------- | -------- |
| 取文字  | `detect()` 就够（不需要样式） | 阅读顺序排序 + 段落合并 + 导出 txt/md                 | 否        |
| 本机打码 | `detect()` 就够        | 敏感信息规则匹配 + 区域遮盖 + 导出无 EXIF                | 否（遮盖是叠加） |
| 图片翻译 | `analyze()`（要样式才能还原） | 调翻译 → 写回 `edit` → **复用现有 `applyEdits()`** | 是，但零新代码  |

**结论：不要为每个功能各写一套检测逻辑。** 检测是这里最贵的一步（几十到几百 ms），三个功能共用同一份结果。

翻译这一条尤其划算 —— 它的"重绘"就是现有的 `applyEdits()`，连溢出处理都能靠 `editParams()` 里已有的 `auto_fit` / `font_scale` 字段解决。

## 2. 架构决策：新建「文字工坊」视图，而不是塞进「无痕改字」

**决定：新增一个视图 `#text`（侧栏名「文字工坊」），内含三个模式页签：取文字 / 打码 / 翻译。**

理由（这条要写进代码注释，不然下次会有人想合并）：

1. **三者共用画布与检测结果**，放同一视图才能天然共享状态，避免重复检测。
2. **与「无痕改字」的定位分得清**：改字 = 逐框精修样式（字体、描边、偏移、字距…）；文字工坊 = 批量语义操作（拿出来 / 盖掉 / 换语言）。前者的 inspector 是重度样式编辑器，混进打码和取文字会互相干扰，`app.js` 会迅速变烂。
3. **两个视图有明确的协作关系**，不是重复建设：翻译模式重绘完可以「发送到无痕改字继续精修」——文字工坊做批量，改字做精修。
4. 对外做产品时，「把图片里的文字拿出来 / 盖掉 / 换语言」本身就是一个独立卖点页。

沿用现有约定：**侧栏一处定义（`shell.js` 的 `NAV`）+ 一个 NAV 项 = 一个视图 + 一组 hash**，不新建页面。

### 关于「两条等价路径」约定

项目约定里写明：**改渲染语义必须同时改浏览器 `web/engine/*` 与 Python `app/*`。**

本方案**不改动任何渲染语义** —— 翻译重绘完全复用现有 `applyEdits()`，样式口径一个字不动。  
因此 Python 侧只需要补一个 `translate` 代理路由，**不需要**同步 `extract.js` 的逻辑（它是纯前端交互层，不参与渲染）。  
这一点请在实施时写进注释，避免以后有人按老约定去两边对拍。

## 4. 三个模式的实现要点

### 模式 1 · 取文字（第 1 期）

输入图片 → `detect()` → 得 `items`（`box / rect / text / score / angle`）→ 排序 → 合并 → 展示与导出。

**阅读顺序排序**（`extract.js`）

1. 先分行：按 `rect.y` 升序排，与当前行中心 y 差超过 `行高中位数 × 0.6` 就另起一行。
2. 行内按 `rect.x` 升序。
3. 竖排/倾斜图用 `angle` / `quad_axis` 判断，第一版只处理水平文本，其余原样输出并标注"未排序"。

**段落合并**（`extract.js`）  
相邻两行若同时满足：左边界接近（差值 < 行高 × 0.5）、行距接近（< 行高 × 1.6）、上一行末尾**不是**句末标点 → 合为一段。否则分段。

**UI**

- 左：原图 + 检测框高亮；鼠标悬停某行文本 → 对应框高亮（复用 `app.js` 里 `scrollToItem` 的同款思路）。
- 右：可编辑的文本区（顺序 = 阅读顺序），支持单行复制。
- 顶部：一键复制全文 / 导出 `.txt` / 导出 `.md`。
- `.md` 导出用字号推断标题层级（该行字号 ≥ 全图中位字号 × 1.4 → `##`，× 1.2 → `###`），这是"扫书/扫资料"场景最实用的一点。
- **明确标注「全程本机，图片不上传」** —— 这是差异化卖点，不要藏在角落。

### 模式 2 · 本机打码（第 2 期）

复用同一份 `detect()` 结果，叠一层规则匹配。

**规则**（`extract.js`，逐条给用户可开关）

- 手机号 `1[3-9]\d{9}`、固话、身份证 `\d{17}[\dXx]`、银行卡 `\d{16,19}`
- 邮箱、IPv4、中国车牌、快递单号（常见前缀 + 数字）
- 「长数字串 `\d{11,}`」作为兜底，但**必须整框命中才算**，否则会把尺寸、金额、编号一起打掉

误伤是这类工具最容易翻车的地方：命中项**默认勾选但全部可见**，用户点一下就能取消。不要静默处理。

**遮盖样式四选一**

- **色块（默认）** —— 敏感信息一律走这个
- 模糊 / 马赛克 —— 只适合人脸、背景杂物这类非关键信息
- **抹字** —— 复用 `web/engine/erase.js`；在纯色背景上直接把文字擦掉，比色块自然。**这是竞品做不到的一点**（手机 App 类打码工具基本只有模糊和马赛克）

**手动补充**：框选任意矩形打码，复用现有 marquee 交互。

**导出**：走 `canvas.toBlob()` 重新编码 —— canvas 编码本身不写 EXIF，**天然就没有 GPS / 机型信息**，不需要手写元数据清理。  
要在自检里断言这一点（见第 7 节），不要靠"应该没有"。

**合规文案（必须落到 UI 和 README）**

> 模糊与马赛克理论上存在被反推的风险，手机号、身份证、银行卡等敏感信息请使用默认的色块或抹字。  
> **不要宣称"无法还原"**，竞品都含糊其辞，我们说实话反而是信任资产。

### 模式 3 · 图片翻译（第 3 期）

`analyze()` → 选源/目标语言 → 批量调 `/api/text/translate` → 译文写回每个 item 的 `edit.text` → **复用现有 `applyEdits()` 重绘**。

**三个难点与对策**

1. **译文变长**（中→英常涨 30~50%，框会溢出）  
   对策完全复用现有机制：先按原 `font_size` 试 → 用 `measureText` 量宽 → 溢出则设 `edit.auto_fit = true` 并降 `font_scale` → 仍溢出才允许按框中心对称扩框。  
   **不要新写一套排版逻辑**，`editParams()` 里已经有 `auto_fit` / `font_scale` / `letter_spacing`。
2. **多语言识别缺口**（这是唯一真正的硬成本）  
   现在装的是 `ch_PP-OCRv3`（中英）。第一期**只支持中 ↔ 英**，日/韩/西里尔等需要换多语言识别模型，列为独立前置任务，不要在第一期里顺手做。
3. **文本必须出境**  
   擦除与重绘在本机，但译文要发到服务端。UI 必须明说「仅文本会发送，图片留在本机」，并沿用现有「把实际发送的内容亮出来」的做法（`image.js` 里已经有这个先例）。

**批次策略**：一次请求打包多行（上限约 30 框），减少往返；响应被截断时自动降半批重试。

**出口**：导出图片（复用现有 PNG/JPG/WEBP 导出口径）+「发送到无痕改字继续精修」。

## 6. 服务端（仅第 3 期需要）

**新路由** `POST /api/text/translate`

```
入参  { texts: string[], from: string, to: string }
出参  { texts: string[] }
```

- 走 `providers` 里 active 的上游（复用现有 `base_url` / `api_key`），模型取新字段 `text_model`
- 未配置 `text_model` 时返回明确错误码，前端降级提示「未配置文本模型」而不是静默失败
- 超时沿用 `MAX_UPSTREAM_TIMEOUT`
- 取文字与打码**完全不碰服务端**，这是它们最大的优势，不要为了"架构统一"给它们加接口

沿用现有 `tools/probe_views.mjs` + `tools/serve_dev.mjs` 的路子（本地自检必须走 `serve_dev.mjs`，它把 `/static/*` 映射到 `web/`；前台跑容易超时，用后台 + 重定向日志）。

| 层   | 断言                                                                                                 |
| --- | -------------------------------------------------------------------------------------------------- |
| 路由  | 侧栏新项存在、`#text-mask` 深链直达、`#create` 等老 hash 仍归一到 `#generate`、切换不重新加载页面                              |
| 取文字 | 用 `samples/` 里的样例图，断言 items 数 > 0、合并后的段落结构快照一致                                                     |
| 打码  | 用合成的"含手机号 + 身份证"图，断言命中项数量、导出后目标区域像素与原图不同、导出 JPEG **不含 APP1(Exif) 段**                               |
| 翻译  | **不测真实上游**（生图 API 失效的教训在前）。mock `/api/text/translate` 返回固定译文，只断言「译文写回 edit」「长译文触发 `auto_fit`／字号下降」 |
| 性能  | 打印检测耗时（沿用现有 probe 的采样写法），确认三个模式复用同一次检测、无重复推理                                                       |

## 8. 风险与边界

1. **OCR 准确率是天花板**：识别错的文字，取文字和翻译都会跟着错。必须保留"手动纠正"的口子（列表可编辑）。
2. **多语言识别**只在第一期覆盖中英，要提前告知，别让用户以为能翻日韩。
3. **打码不能宣称不可还原**；敏感信息默认色块或抹字。
4. **翻译文本出境**必须明说，否则「本机处理」的信任叙事会崩。
5. **长图/超大图**：`detect()` 已有 `maxSide = 2400` 的降采样，但取文字场景常见长截图，要单独确认超长图的坐标映射与内存占用。

## 9. 明确不做（范围边界）

- **不做**生图相关的新功能（API 已失效，也不在本方案范围）。
- **不做**人脸识别打码、不做 AI 换脸、不碰身份证件本身的正片处理（合规红线）。
- **不做**"疑似姓名/机构"的自动识别（需要模型或词典，误伤率高，标为实验特性都不做）。
- **第 4 期（截图转表格）先不进入实施**：它的胜负手是准确率（复杂表头、合并单元格），需要单独啃表格线检测与结构还原，和上面三个不是同一量级的活。等前三个上线、手感验证过再说。
