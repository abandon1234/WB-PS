# 图片文字处理与生成工具

一个统一的「图像工作台」：无痕改字 + 图像生成，共用一套侧边栏外壳。

---

## 先选版本：这个项目有两套后端

**前端只有一份（`web/`），两个版本共用**；区别只在"跑在哪、后端用什么"。

| | **本地版（Python）** | **Cloudflare 版（Workers）** |
|---|---|---|
| 后端 | `app/` · FastAPI | `cloudflare/src/` · JS Worker |
| 前端托管 | Python 直接托管 `web/` | `web/` 同步到 `cloudflare/public/static/` |
| 启动 | `start.bat` / `start.sh` → `http://127.0.0.1:8000` | `cd cloudflare && npm run deploy` |
| 无痕改字 | Python 本地推理（OpenCV / ONNX） | **浏览器内推理**（WASM，服务端不参与） |
| 配置存储 | `data/` 本地文件 | Cloudflare KV |
| 适合 | 离线用、想本地跑模型、二次开发 | 要公网访问、不想维护服务器 |

- **本地版**详见本文档（下面所有内容默认讲它）
- **Cloudflare 版**详见 [`cloudflare/README.md`](cloudflare/README.md)

> 两个版本**共用同一份前端源码 `web/`**。
> 改前端请改 `web/`，Cloudflare 版用 `npm run sync:assets` 同步过去；
> `cloudflare/public/static/` 是**同步产物，不要直接编辑**。

## 统一外壳

所有页面共用 `web/shell.css` + `web/shell.js`（`/admin` 除外）：

- **侧栏一处定义**，导航项是普通 `<a href>`，指向同一页的不同 hash
- 分组：`图片工具`（无痕改字 / AI 生成）、
  `资源`（作品库，带实时数量徽标）、底部本机占用条 + 后台入口
- **深链**：`/#generate` 直达生成视图，`/#projects` 直达作品库，
  `/#text-mask` 直达改字视图的打码页签
- 图标雪碧图由 `shell.js` 统一注入，各页面不再各抄一份
- 侧栏折叠状态存 `localStorage`，窗口窄于 1100px 时**首次自动折叠**，之后完全听用户的

> **改字与生成曾是两个独立页面**（`/` 与 `/image`），来回跳转每次要重新初始化
> 本地引擎（切回改字实测 5.77s）。现已合并为**单页多视图**：`web/index.html`
> 里并列 `#viewEdit` / `#viewImages`，切视图只换显隐、不重载，实测 **9~29ms**。
>
> 曾经还有一个并列的 `#viewText`「文字工坊」视图，现已**整体并进无痕改字的右栏**
> —— 它和改字共用同一张图、同一次识别、同一块画布，本就不该是两个入口。
> 侧栏因此从四项回到三项。

`/admin` 刻意不引入外壳——它是独立外观，一眼能看出是「管理区」。

### 外壳上修掉的两个 bug

**① 侧栏折叠后展不开（会把自己锁死）**

折叠态下品牌行还是横排（logo 27px + 间距 + 按钮 26px），而侧栏只有 62px 宽，
折叠按钮被压成 **0 宽**并被 `.sb-brand` 盖住 —— `elementFromPoint` 命中不到它。
用户点一次「收起」就再也收不回来，只能清 localStorage。
另外窄屏的媒体查询**无条件**把侧栏压成 62px，连类名都不看，让这个问题更隐蔽。

改法：折叠态品牌行改竖排（logo 在上、按钮在下，28×28 保证命中面积）；
把「强制折叠」从媒体查询移进 JS，只在没有用户偏好且窗口 < 1100px 时自动折叠一次；
折叠按钮的 `title`/`aria-label` 随状态在「收起/展开侧栏」间切换。

**② 尺寸/数量菜单关不掉，一直浮在界面上**

`closePop()` 只把遮罩 `#popWrap` 设成 `hidden`，而 `#pop` 面板是 **`document.body` 的子节点**
（不是遮罩的子节点），`position: fixed` 又不受 `body` 的 `overflow:hidden` 影响 ——
于是遮罩没了，菜单还留在屏幕上；只有下次打开别的菜单才会被 `openPop` 里的
`old.remove()` 顺手清掉。改成把面板挂进遮罩内部，隐藏遮罩即隐藏菜单；
定位也改成先量尺寸再摆位，上方放不下就翻到下方，都不行再夹进视口。

两个 bug 都固化成了断言，见 `node tools/ui_shot.js --verify`。

# 模块一：无痕改字（图片文字处理）

扫描图片中的文字，识别其**内容与位置**，还原**字体、字号、颜色、粗细**，
并在原位置做**无痕修改替换**——改完看不出动过手脚。

## 工作区断点续做

切到生成视图再切回来，编辑状态不会丢。实现分两层：

- **本机持久化**：`web/workspace.js` 把工作区落到浏览器 IndexedDB，拆两张表——
  `meta` 放轻量状态（session_id / 识别结果 / 改动 / 视图），每次编辑都写；
  `image` 放原图字节，只在换图时写。混在一张表里的话，每敲一个字都要重写几 MB 原图。
- **服务端会话复用**：`GET /api/session/{id}` 把仍在内存里的识别结果原样读回
  （**不重跑 OCR**）。会话还在就直接复用；服务重启后会话没了，
  就用本机存的原图重新识别，并按「item id → 原文 + 位置」两级兜底把改动映射回去。

改动样式回填走 `POST /api/preview-batch` 一次拿全补丁，
而不是 N 处改动发 N 次请求——顺带把 `applied` 区域填好，之后单条「重置」才有依据。

落盘时机：编辑一轮结束（预览返回）立即写；另有 400ms 防抖兜住连续输入，
再叠加 `pagehide` / `visibilitychange` 收尾，保证跳转前一定写进去。

想主动丢弃时点工具栏的**关闭图片**，会同时清掉本机快照。

## 自定义字体

系统字体之外，可以把**自己的字体**加进来用于替换。

**方式一（推荐）**：编辑面板 → 字体 → **导入字体**，选 `.ttf` / `.otf` / `.ttc`，
立即生效，不用重启服务。已导入的字体在下拉框里带 `★` 前缀。

**方式二**：把字体文件直接拷进项目根目录的 `fonts/`，点 **重新扫描**（或重启服务）。

说明：

- `fonts/` 的优先级**高于系统字体**，同名族会优先用这里的版本
- `.ttc` / `.otc` 是字体集合，内含多个字体会自动逐个登记
- 删除文件后同样需要「重新扫描」才会从列表消失
- 只接受字体扩展名，且落盘前会校验能否被解析，无效文件不会残留
- 字体文件的增删会让扫描目录的 mtime 变化，缓存自动失效，不需要手动清缓存
- `fonts/` 里的字体文件已在 `.gitignore` 中排除，避免把有版权的商业字体分发出去

## 两大核心能力

### 1. 文字识别与定位

- 输出每个文本块的**四点坐标**（可表达倾斜）与**轴对齐矩形**
- 同一行的碎框自动合并成「文本行」，编辑体验与视觉还原都更自然
- 长边超过 2400px 自动降采样加速，坐标映射回原尺寸

### 2. 无痕修改与替换

这不是"盖一块色块再写字"，整条链路有六处针对"不露痕迹"的设计：

**① 样式反推：颜色**
不用平均值（抗锯齿像素会把颜色拉灰）。做法是以背景色为基准，
取偏离最大的那批像素（真实墨迹核心）的众数颜色。

**② 样式反推：字号**
由**墨迹高度**反推，而不是 OCR 框高度（框含 padding，不可靠）。
且不用经验系数——渲染前会**实测**所选字体参考字的字面比例
（例如微软雅黑汉字 0.908、黑体 0.883、Arial 大写 0.717），
因此换字体后字号依然对得上。

**③ 样式反推：粗细 / 背景**
粗细用「笔画宽度 ÷ 墨迹高度」判定（距离变换峰值），不依赖字体元数据。
背景分为**纯色 / 渐变 / 纹理**三类，各自走不同的擦除策略。

**④ 精确掩膜**
用**局部背景图**（形态学开/闭运算估计）做差分，而不是全局阈值——
后者会把渐变背景整片误判成文字。掩膜只保留与目标框重叠的连通域，
避免擦到上下相邻的行。擦除用途关闭连通域去噪，
否则文字顶部的细小抗锯齿碎片会被当噪点剔除，留下淡淡轮廓。

**⑤ 分级擦除 + 残留自检**

| 背景 | 策略 | 原理 |
|---|---|---|
| 纯色 | `fill` | 用紧贴掩膜外圈的真实像素估色后整块填充（不需要羽化，羽化反而造软边） |
| 渐变 | `linear` | 逐列/逐行用掩膜外侧像素做线性外推，取接缝更平滑的方向 |
| 纹理 | `inpaint` | OpenCV Telea / NS 内容修复 |

擦完会**自动检测残留**（框内边缘能量 ÷ 周边背景边缘能量），
偏高就逐轮加大掩膜重擦，最多三轮。

**⑥ 贴合渲染**
- 4 倍超采样绘制后缩回，边缘平滑度接近系统抗锯齿
- 逐字符布局 + 以基线为锚点，跨字体基线一致、支持字距
- 对齐的是**墨迹外接框**而非 OCR 框，消除字体上升/下降部造成的错位
- **清晰度匹配**：原图若经 JPEG 压缩、文字边缘偏糊，按原图锐度对新文字做等量柔化，否则新字会"太锐"而露馅
- **不因原框宽度而改字号**（默认行为）：字变小比"略超出原位置"更容易被一眼看出来，
  而实际场景里文字旁边多半是空白。只有溢出到会盖住相邻内容（超过 1.8 倍）
  才收敛字号，且不低于原字号的 72%。想主动压回原宽度可在面板勾选「过宽时缩字号」。
- 宽度比较一律用**墨迹 bbox**，而不是渲染图层的画布尺寸——图层左右带有约
  0.35×字号的透明 padding，拿画布宽去比会凭空多出几十像素，
  导致"过宽"判断几乎每次都误命中、字号被无故缩小。
- **垂直按底部（基线）对齐**（默认）：阅读时的视觉锚点是基线，按基线对齐最不容易
  看出被改过。若改成居中，新旧文字墨迹高度稍有不同就会把整行推走。
  可在面板切换为居中 / 顶部。
- 墨迹外接框用 **alpha 阈值**测量，而不是 `getbbox()`——LANCZOS 缩放的振铃会在
  字形外围留下极低 alpha 的伪影，`getbbox()` 会把它算进"内容"，
  实测能让墨迹高度虚高 40px 以上，进而把垂直定位整体带偏。

**⑦ 字体与粗细还原（决定"像不像"的关键）**

字体族用**两阶段匹配**：

1. 用「墨迹宽高比 + 墨迹填充率 + 笔画比」从**常用字体白名单**里筛候选
   （不做白名单限制会选中 ITC Bookman 这类"比例接近但字形无关"的冷门字体）
2. 拿**原文字在图中真实的墨迹轮廓**，与候选字体的渲染轮廓做形状 IoU，取最高者

第 2 阶段是必要的：低维特征区分不了 Segoe UI vs Trebuchet MS、
Helvetica vs Calibri（得分几乎打平），而形状 IoU 是拿真实笔画轮廓直接比，能分辨。
注意匹配用的是**原文字**——那才是图里真实存在、可以和模板比对的形状。

笔画粗细做**闭环校准**：渲染 → 用与测量原图相同的口径测笔画宽度 → 补描边 → 再测，
最多两轮。即使字体本身偏细，也能补到与原图一致；若原文字更细，
会尝试切到同族的 Light / Thin 变体。

匹配前会过滤掉**渲染不出该文本的字体**（例如用 Calibri 去画中文）——
否则墨迹度量整体失真（实测会把字号算成 1.7 倍）。

### 3. 「要不要动图」的判定只有一份实现

`S.edits` 里放什么引擎就照着重绘，但"这一项到底算不算改过"这件事，
**UI 与引擎必须共用同一份判据**（`web/engine/dirty.js` 的 `isDirty`）。

这不是洁癖，两边各判一套会这样裂开：

| 谁 | 旧判据 | 后果 |
|---|---|---|
| UI（`app.js`） | 字段被设过就算改 | 判"改了"就立刻贴本地预览补丁 |
| 引擎（`applyEdits`） | 必须真的和原文/原样式不同 | 判"没改"就完全不擦不画 |

而**预览补丁的擦除范围是 `rect` 外扩**（`erase.js` 的 `pad = clamp(h*0.9, 8, 48)`，
单行文字实测约 22px）——框外的东西会被一起擦掉。于是：

> 原图是「聚缘快捷宾馆1」，OCR 只识别出前 6 个字。
> 用户动了一下那一项（最终值与现状等价）→ UI 贴补丁，把框外的 `1` 一并擦掉 → 界面 6 字；
> 引擎判「没改」→ apply 根本不擦不画 → 结果图 = 原图，7 字。
> 界面上就成了"我改的是 6 字，生成出来 7 字"。

判据本身不复杂，难的是**只能有一份**。两个配套细节：

- UI 侧是动态 `import('./engine/dirty.js')`（必须自己拼 `?v=`），
  并在 `restoreWorkspace()` 前 `await DIRTY_READY` —— 否则恢复工作区时会按错口径渲染一遍。
- Python 侧的对应实现是 `app/pipeline.py` 的 `_dirty`，改 `dirty.js` 要同时核一遍那边。

`tools/probe_edit_panes.mjs` 的 `[6] 改动判定：UI 与引擎同口径` 盯着这条约定
（把 UI 判据换回旧版，该用例会红）。

# 模块二：取文字 / 打码 / 翻译（无痕改字右栏页签）

三者已并进「无痕改字」的右栏，是**改字 / 打码 / 翻译 三个页签**，
共用左侧同一张图、同一次识别结果、同一条 `edit` 契约。

## 为什么是三个页签，而不是三个独立视图（更不是三个入口）

三者的前半段完全一样，差别只在「后半段输出什么」：

| 页签 | 用到哪一段 | 输出 |
|---|---|---|
| 改字 | `analyze()` | 逐框改文字与样式（识别结果本身就是「整页文字」） |
| 打码 | 同一次 `analyze()` | 敏感信息遮盖（色块 / 马赛克 / 模糊 / 抹字） |
| 翻译 | 同一次 `analyze()` | 译文写回 `edit`，复用现有 `applyEdits()` 重绘 |

检测是这条链路里最贵的一步（首次还要下 39MB 模型），三件事绝不该各跑一遍。

**曾经的做法**是另开一个 `#viewText`「文字工坊」视图、三套模式各一块画布 ——
结果必然长出「切模式就丢图、缩放归零、识别重复跑」那一堆问题，因为三份状态
各自持有同一张图。现在改成**一页三键**：一块画布 DOM、一份识别结果，
点按键只换右侧 `<aside class="pane">`。

### 公共契约：`S.edits`

改字早就有 `S.edits[id] = { text, font, size… }`，这**天然就是**另外两件事的接口：

- 打码的「抹字」= `{ text: '' }`（改字里「留空则仅擦除」本来就是合法语义）；
- 翻译 = `{ text: 译文, auto_fit: true }`。

所以打码与翻译**完全没有各自的排版/重绘代码**，写进 `edits` 之后走的就是
改字那条预览 / 导出通路，连溢出处理都靠 `editParams()` 已有的 `auto_fit` / `font_scale`。

### 遮盖层是「图的属性」，不是页签的属性

画布是三层同尺寸位图：`imgLayer` → `maskLayer` → `boxLayer`。

- **色块 / 马赛克 / 模糊走前端 canvas 直接画**（实时预览，不走引擎）；
- **抹字走引擎擦除**（`/api/text/erase`），因为它要真的把像素补掉。

遮盖画在 `maskLayer` 上，所以切页签、切视图都不会丢；导出时由 `burnMasks()`
把它烧进最终 blob —— 预览与导出**共用 `drawMasks()`**，不写第二份绘制代码。

## 取文字（复制全部 / 导出 txt）

「取文字」不单设功能键：**识别结果本身就是整页文字**，出口就是改字列表上方的
`复制全部` / `导出 txt` 两个按钮。

- 按**阅读顺序**重排（不是 OCR 的原始顺序），走 `extract.extract(items)`；
- 「复制全部」优先 `navigator.clipboard`，非安全上下文回退 `execCommand`；
- 「导出 txt」按阅读顺序落文件；未识别出文字时两个按钮都是 disabled。
- 排序与分段全在 `web/engine/extract.js` 里完成，是纯函数，不碰 DOM 也不下模型。

### 排序与分段（`web/engine/extract.js`，纯函数）

输入是 `detect()` 的 items，输出是文本，中间不做任何像素操作：

1. **分行**：按框中心 y 升序，与当前行中心差 ≤ 行高中位数 × 0.6 归为同一行；
   行内按 x 升序。高度量级差太多的不并（大标题紧挨着的小字是两行）。
2. **分段**：相邻两行同时满足才并成一段 —— 左边界接近（< 行高 × 0.5）、
   行距正常（< 行高 × 1.6）、**两行字号相当**（行高比 ≥ 0.62，挡住"标题并进正文"）、
   上一行末尾不是句末标点。
3. **拼接**：两侧都是 ASCII 词字符时补一个空格，中文之间直接相连；两片**贴得极近**
   （间隙 ≤ 行高 × 0.34）时不加空格 —— 那多半是同一个词被 OCR 切碎了。
4. **md 标题层级**：按行高推断（≥ 全图中位行高 × 1.4 → `##`，× 1.2 → `###`）。
   用行高而不是 `style.font_size`，因为取文字不跑样式分析、拿不到字号；
   同一行里行高与字号是等比关系，替代是等价的。段内多行会合成一行
   （OCR 的换行是排版换行，不是语义换行），但整段都是列表项时保留逐行。

> ⚠️ **与「两条等价路径」约定的关系**：项目约定「改渲染语义要同时改
> `web/engine/*` 与 `app/*`」，但 `extract.js` **不参与渲染**，不涉及任何
> 像素 / 字体 / 描边口径，所以 Python 侧不需要再实现一份。那条约定只管
> 渲染（`web/engine/render.js` ↔ `app/text_renderer.py`），别按老规矩去两边对拍。

## 打码（右栏「打码」页签，老链接 `/#text-mask`）

分享截图前把敏感信息盖掉。**全程本机**：识别与遮盖都不联网，图片不上传。
默认用的就是改字那一次 `analyze()` 的结果，不额外跑检测。

### 识别规则（`web/engine/mask.js`，纯函数层）

| 规则 | 形态 | 说明 |
|---|---|---|
| 邮箱 | `xx@yy.zz` | |
| 车牌 | 省份简称 + 字母 + 5~6 位 | 含新能源与"挂 / 学 / 警 / 港 / 澳" |
| IP 地址 | 四段点分 | 每段要 ≤255，`999.999.999.999` 不打 |
| 身份证 | 18 位（末位可 X） | |
| 银行卡 | 16~19 位数字 | |
| 手机号 | `1[3-9]` 开头 11 位 | |
| 固话 | 区号 + 号码 | |
| 长数字串 | ≥11 位数字 | **兜底**，见下 |

三条关键设计：

- **数组顺序 = 优先级**。先匹配的占用字符区间，后面的规则跳过重叠部分 ——
  不这么做的话，18 位身份证同时满足「16~19 位数字」，会被标成"银行卡"。
  另外命中两侧不能挨着数字，否则从 19 位卡号里会截出 18 位来。
- **兜底规则必须整框命中**。「订单号 202610131234567」里的 11 位数字、尺寸、
  金额都不该被打掉。宁可漏（用户还能手动框选补），不可误伤
  （误伤了往往到发出去才发现）。
- **兜底会给被关掉的规则让路**。关掉「手机号」后，11 位数字如果还被「长数字串」
  打掉，那个开关就等于没生效 —— 所以兜底命中前会先问一句"这一段是不是本来
  该由某条（被关掉的）具体规则负责"，是就让开。

### 落在哪个框上

**能落到单个文字框就绝不整行盖。**「电话 13800138000」如果 OCR 给的是一个框，
那只能盖整框；但若是「电话」+「13800138000」两个框，就只盖号码。
逐框匹配优先，整行匹配只作为兜底 —— 兜住"号码被 OCR 切成两半"的情况。

命中项**默认全选但逐条可见可取消**，不静默处理。**手动框选**（在图上拖拽）也能补一块：
拖出来的矩形直接进列表，和自动命中项一样能勾掉、能换遮盖档。

> 框选只在打码页签生效（`S.pane === 'mask'` 时才 `cursor: crosshair`），
> 拖拽阈值按**显示尺寸**算（>4px 才算框），否则「点一下文字框」会被误判成拖框。

### 四种遮盖

| 档位 | 怎么实现 | 适合 |
|---|---|---|
| **色块**（默认） | canvas `fillRect` | 敏感信息一律走这个 |
| 马赛克 | 该区域缩到很小再关掉平滑放大回去，**块取框高的 40%** | 人脸、背景杂物 |
| 模糊 | canvas `filter: blur()` + 裁剪重绘 | 同上 |
| 抹字 | 走引擎（`/api/text/erase` → `erase.js`） | 纯色背景上最自然 |

前三种是 canvas 原生能力，**前端直接重绘**（画在 `maskLayer` 上），零延迟实时预览；
只有抹字要引擎参与 —— 它走的是改字那条「把文字置空」的通路（`edits[id] = {text:''}`），
所以**不占用遮盖层**，切档位时还要把写空的文字还回去。
预览与导出**共用同一个绘制函数**（`drawMasks()`，只差一个 scale），
所以「看到的」必然等于「导出的」—— 两套绘制代码早晚会漂移。

马赛克的块大小刻意取粗（框高 40%，不是常见的固定小值）：取小了会保留字形轮廓，
眯着眼还能认出来，那就白打了。

### 抹字怎么保证擦干净

实拍反馈过一件事：抹完字没了，**但原地留着一片灰**。查下来是「取色」出的问题 ——
填充色取自掩膜外圈，而外圈紧贴字形，混进了抗锯齿的灰边；中位数被那些灰像素一拖就
偏灰，整块填出来就是淡灰带。同一张图上换成紧贴邻行的字（或掩膜退化成整框）时更严重：
外圈直接压在邻行的笔画上，整框都刷成灰。

现在的取色是三层递进，任一层不像背景就往下退：

| 层 | 怎么取 | 什么时候用 |
|---|---|---|
| 1. 掩膜外圈 | 外圈灰度**主峰所在簇**的均值（不是中位数），且主峰簇占比 ≥ 0.70 | 外圈确实是背景时 |
| 2. 整个 ROI | ROI 主峰簇的均值（ROI 高度是框的 3 倍，绝大多数像素是背景） | 外圈被邻行的字占住时 |
| 3. `style.bg_color` | 样式分析给的颜色 / 白 | 上面都不可信时 |

再加上一道**残影清扫**：纯色底（判定依据是「框外那圈的主峰簇占比 ≥ 0.80」）上，
落在「原文字掩膜外扩 5px ∩ 目标框」范围内的像素，只要偏离背景超过 12 就归到背景色。
范围不外扩到整个框，是为了 OCR 行框常常比字高、别把框里离文字很远的邻行字头一起抹掉。

> 刻意**不做**的一件事：保护恰好压在清扫范围内的表格线。试过按"横贯整行"识别它，
> 但判据做不到既可靠又不留残影 —— 而留残影正是这里要修的问题。取舍是宁可少一道线。

`auto` 也顺势改准了：以前 `style` 缺席时（抹字就是这种情况）一律当纯色底走 `fill`，
在照片上会糊出一块假平面；现在先用框外那圈判"是不是纯色底"，纯色才填充，
有纹理交给 `inpaint`。

### 一个只坑浏览器侧的坑：非连续 Mat 的 `.data`

上面那套取色/填充/清扫**只能在 `ptr(row)` 上做，不能碰 `Mat.data`**。

`crop` / `clone` 出来的多通道 Mat，实测 `isContinuous()` 为 `false`，而 `data.length`
又恰好等于 `rows × cols × channels` —— 于是按平铺下标读写**不报错、看着也有值，
但整体对不上号**。踩到的后果很隐蔽：`fillPatch` 以为自己在往掩膜像素上刷背景色，
实际刷在别处，文字原封不动留在真实内存里；而度量函数（走 `cvtColor`，读的是真实内存）
如实报出残留 —— 于是界面上一片「抹字有残留」，输出图却因为粘贴时用了**同一套错位读法**
而看着干干净净。同理，`sweepResidue` 的写入也一直没落到真实像素上，**残影清扫等于没生效**。

这个坑 `web/engine/cvutil.js` 的 `planeData` 注释里早就写过（1 通道掩膜上已经绕开），
但 `erase.js` 里 `fillPatch` / 最终粘贴 / `ringBgColor` / `roiBgColor` / `blurPatch` /
`linearPatch` / `interpAxis` 一度还在用平铺 `.data`，现在**一律逐行 `ptr(row)`**。

判据很简单：**单通道且连续的掩膜可以平铺；只要是多通道（BGR），就必须 `ptr(row)`。**

回归手段是 `tools/dbg_erase_harness.mjs`：直接调 `/api/text/erase` 跳过 OCR，
五个场景（纯色 / 深色 / 灰底 / 渐变 / 纹理）的输出与 Python 同构实现**逐像素对拍**
（`tools/dbg_diff_js_py.py`），必须全部 `maxΔ = 0`。

### 抹字的残留自检

擦完**逐块回报两把尺子**，超过阈值就在界面上说「有 N 处没擦净，这类内容建议改用色块」。
理由很直白：抹字留了残影而用户以为盖好了，比不盖更糟。

| 尺子 | 量什么 | 阈值 | 用在哪 |
|---|---|---|---|
| `leftover_max` | 清扫范围内**最大离背景偏移**（0~255） | > 16 | 纯色底 —— 擦净是 0~3，一道灰痕立刻上到几十 |
| `leftovers` | 区域内**灰度标准差** | > 8 | 有纹理的底子 —— 那种底"离背景多远"没有判别力 |

状态条与「遮盖 N / M 处」并排显示结论：`抹字已擦净` / `抹字有残留(峰值)`。只在
结果确实对应当前命中集（签名一致）时才报，避免改了勾选还显示旧结论。

> ⚠️ 两把尺子都刻意**不用** `erase.js` 的 `meta.residual`（内区边缘能量 ÷ 外圈边缘
> 能量）：擦净的纯色底上它确实降到 0，但它是个**比值** —— 纹理底上分子分母都被纹理
> 同时抬高、反而逼近 1，判别力不如上面两把绝对量的尺子。所以结论只认 `leftover_max` /
> `leftovers`，`residual` 退居为「选策略时逐轮比较」用。
>
> （早期这里写的是「residual 恒在 100 量级、没有判别力」—— 那是
> `fillPatch` 平铺错位那个 bug 的症状，不是它的固有性质；bug 修掉后就正常了。）

### 导出

走 `canvas.toBlob()` 重新编码。canvas 编码**本身不写任何元数据**，所以 GPS、
机型那些原始信息天然不会跟着出去，不需要手写清理。自检里断言这一点
（扫 JPEG 段找 `FFE1`），不靠"应该没有"。

### 合规红线（已落到界面文案）

> 模糊与马赛克理论上存在被反推的可能，手机号、身份证、银行卡请用色块或抹字。

**不宣称"无法还原"** —— 竞品都含糊其辞，我们说实话反而是信任资产。
另外不做人脸识别打码、不做证件本身的正片处理。

## 翻译（右栏「翻译」页签，老链接 `/#text-translate`）

**只有这一件事要联网**：识别、擦除、重绘全在本机，出网的只有"从图里识别出来的
那几行文字"。界面上把实际发送的内容原样列出来（`本次发送出去的文字`），
这是"本机处理"这条叙事能不能立住的关键——藏着不说，前面那些功能的信任就白攒了。

**这是结构性保证，不是自觉**：`/api/text/translate` 的入参**只有 `texts[]`，
收不到图**。也就是说，就算想把图片传出去也传不了。

**为什么用 `analyze()` 而不是 `detect()`**：译文要按原样式画回去，必须拿到
字体 / 颜色 / 描边 / 字号。代价是多跑一遍样式分析，换来的是**重绘这一层零新代码**。
而且改字本来就要 `analyze()`，所以「多跑一遍」实际是**一次都没多跑**。

### 重绘完全复用现有管线

译文写进 item 的 `edits[id] = { text, auto_fit: true }`，剩下的交给
改字同一条预览 / 导出通路——擦除、字体匹配、描边校准、过宽收缩全是改字在跑的
同一套。**翻译侧没有新写一行排版代码**：

1. `auto_fit = true`（界面上的「过长缩字号」）：中→英常涨 30~50%，
   按原字号必然溢出。开了它就落到 `render.js` 已有的收敛逻辑里，
   缩到框宽 1.15 倍以内为止，缩过的行会在界面上标出来（`pair.fitted`）。
2. 逐行对照可手改：改完去抖自动重绘，改一个词不用重新跑一次翻译。

### 批次与降半批重试

一次最多打包 30 行（`TR_CHUNK`）。**行数对不上就劈成两半各翻一次**，最多劈 3 层
（`translateChunk`）。这是这类调用最常见的失败（模型漏行 / 被截断），
而"整批重来"在 30 行时几乎必然再失败一次，降半批能很快落到能成功的粒度。

### 上游与配置

`POST /api/text/translate` → 中转站的 `/v1/chat/completions`，模型取 provider 的
**`text_model`**（后台「中转站配置」里单独一栏）。

> 为什么不复用生图那个 `model` 字段：`gpt-image-2` 做不了文本翻译。
> 也刻意**不给默认值**——随便塞一个默认只会让用户拿到一堆看不懂的上游报错，
> 不如一开始就说清楚：没配 `text_model` 时接口返回「未配置文本模型」，
> 界面直接把这句话显示出来。

上游解析是宽松的：剥 ``` 围栏、认 `{"texts":[...]}` 与裸数组两种形状、
退一步还能按行拆。**唯独行数对不上不猜**——错位的译文贴错位置比不翻更糟。

### 出口

- **写回画布**：把译文当作一批 `edits` 交给 `WBEdit.applyEdits()`，就地预览。
  因为翻译本来就在**改字视图里**，所谓"交接"只是同一块右栏换个页签 ——
  不需要把原图 / 会话 / items 写进工作区再让另一个视图重读。
- **撤销译文**：把这批译文 id 从 `edits` 里摘掉，画面回到原样。
- 最终导出与改字共用同一条 `导出` 通路（含有遮盖图时一并烧进 blob）。

### 硬约束（说在前面）

**本期只支持中 ↔ 英**。现装 OCR 是 `ch_PP-OCRv3`（中英），日 / 韩 / 西里尔
识别不出来，也就没有可翻的东西——换多语言识别模型是独立的前置任务。

完整设计见 `docs/plan-text-workshop.md`（记录的是当年另开视图的方案；
后来改成「并进无痕改字右栏三页签」，该文档保留作为决策过程）。

## 生成视图（面向使用者，`/#generate`）

## 一个工具，两种模式

合并前是四个工具（自由生成 / 图像融合 / 人物写真 / 商品图生成），但它们的流程**完全一样**：
填提示词 →（可选）传参考图 → 生成。差别只在提示词怎么写、要不要参考图，
所以现在由「有没有传参考图」自动决定语义：

| 情况 | 参照图 | 默认尺寸 | 发给模型的内容 |
|---|---|---|---|
| 纯文生图 | 不传 | 1024×1024 | 提示词**原样发送**，不做任何改写 |
| 带参考生成 | 选传 1~4 张 | 1024×1024 | 前面加一句「以参照图中的主体为准，保持其外观、五官、发型、比例与颜色等特征不变…」；要求光照、阴影、色温与场景统一，主体边缘自然，不改变主体本身，不要出现拼贴或抠图痕迹 |

任务细节（写真、电商主图、把主体融进新场景）直接写进提示词，快捷短语里有现成的例子，
所以原来那四种玩法一个都没丢。

配套的几处一致性处理：

- **传了参考图就说清楚图会被怎么用**：参照图区出现「已传 N 张：生成时以参照图的主体为准
  （外观保持一致），只按提示词换场景与风格」，舞台空态同步变成「参考图已就绪」。
- 结果区标注**工具名与尺寸**，并在加了指令时把**实际发送给模型的提示词**整段亮出来
  ——包装过程对用户是可见的，不然「我明明写得很短，怎么出来这么长一段」会很莫名。
- 作品库卡片带工具徽标，一眼能看出是哪次生成的。
- 提示词包装放在**前端**而不是服务端，就是为了让「实际发送了什么」可以被看到。
  服务端只接收并回显 `tool` 标识（`tool_name` 一并返回，用于结果标注）。


## 草稿与本机缓存

生成区只有一份草稿：提示词、尺寸、数量、参照图、上一张结果，边写边存，
切视图（去改字那边转一圈）或者刷新页面回来内容都还在。

**合并前的老草稿会被接手**：启动时读本机草稿，若新键 `generate` 没有记录，
就取 `create` / `combine` / `portrait` / `product` 里 `savedAt` 最新的一条继续用
（参照图也按老键读一次），用户不会因为这次合并丢东西。

草稿同时落到**浏览器本机**（`web/toolcache.js`，IndexedDB）：

| 存什么 | 存在哪 | 说明 |
|---|---|---|
| 提示词 / 尺寸 / 数量 / 停在第几张 | `state` 表 | 每次编辑都写，只有几十字节 |
| 参照图字节 | `assets` 表 | 只在参照图增删时写，按工具键存 |
| 上一张结果 | 只记作品库的记录 id | 生成时已自动入库，不重复存字节 |

几个刻意的设计：

- **拆两张表**。混成一张的话，每敲一个字都要重写几 MB 的参照图。
- **结果图不复制字节**，只记记录 id。代价是：把某张图从作品库删掉，舞台上
  缓存的「上一张」也会跟着消失——那是用户主动删的，符合预期（并且这条已写进回归断言）。
- **单独一个数据库** `wb-image-tools`，不与作品库共用。同一个库名用不同 version
  打开会触发 blocked，排查起来很痛苦。
- **落盘时机三层叠加**：编辑后 350ms 防抖 → 切视图时立即写 → `pagehide` /
  `visibilitychange` 兜底。只靠防抖不够，切页可能正好落在防抖窗口里。
- 参照图与结果图**按需补取**：切到某个工具时才去读它的参照图字节与结果记录，
  不在启动时把四份全读进内存。

## 密钥是怎么被隔离的

这是本次改动的重点。**任何接口都不会把 API Key 下发给前端。**

1. **两套接口前缀**：生成页只依赖 `/api/image/status` 与 `/api/image/generate`；
   配置类接口全部搬到 `/api/admin/*`，必须登录才能访问。
   原来下发明文 key 的 `/api/image/overview`、`/api/image/providers` **已彻底删除**
   （访问返回 404）。
2. **默认打码**：`config.public_view()` 的 `reveal` 默认值改为 `False`，
   凡是走到 HTTP 响应的配置一律显示成 `sk-BSp******r4si`。
   只有服务端内部调 `get_provider()` 才拿得到明文，用于真正发起请求。
3. **管理密码**：PBKDF2-HMAC-SHA256（12 万次迭代 + 16 字节随机盐）存哈希，
   落在 `data/admin.json`。**没有默认口令**，首次打开 `/admin` 由使用者自己设定。
4. **会话令牌**：HMAC 签名 + 12 小时过期，放在 `HttpOnly; SameSite=Lax` Cookie 里，
   前端 JS 读不到，页面即使出现 XSS 也拿不走凭证。
5. **登录限速**：同一 IP 连续 6 次密码错误锁定 5 分钟。
6. **忘记密码**：停止服务 → 删除 `data/admin.json` → 重启后重新设置。服务端不留后门。

## 生成结果存在哪

**服务端不保存任何生成图片。** 图片以 data URL 直接回给浏览器，
前端转成 `ArrayBuffer` 存进本机 **IndexedDB**（`wb-image-studio`）：

- 库内**拆两张表**：`meta` 放元数据 + 360px 缩略图，`blobs` 放原图字节。
  如果混在一张表里，画廊遍历游标会把每张 2MB 的原图都读进内存——
  50 张就是 100MB 的 I/O。拆开后画廊只读几十 KB 的缩略图，点开灯箱才取原图。
- 记录提示词、模型、尺寸、工具、时间、收藏等元数据，支持搜索与筛选。
- 清空浏览器数据即彻底消失；`data/` 目录里除了配置没有任何图片。
- 支持 `/#projects` 深链直达作品库。

## 中转站协议（实测结论）

对接过程中验证出四条关键事实，都写进了 `app/image_gen/client.py`：

1. **参照图走 `/v1/images/generations` 的 `image` 字段**（data URL），
   而不是标准 `/v1/images/edits`——后者在这类中转站上直接返回空 `data`。
2. **多参照图同样走 `image` 字段，传数组即可**，不必退化成拼图。
   实测（洋红底白方块 + 青底黑三角两张强特征图）：结果图洋红占比 75.3%、
   青 19.3%，**两张都被采纳**。前端仍保留"被拦时自动改拼图重试"的兜底。
3. **`b64_json` 返回的是 data URL**（带 `data:image/png;base64,` 前缀），
   不是纯 base64；直接解码会因长度非 4 的倍数而报错，需要先剥前缀再补 padding。
4. 内容被拦截时接口可能返回 **HTTP 200 + 空 data**，需要显式识别并给出提示。

## 已知限制

- **字体识别是"匹配"而非"识别"**：系统从常用字体里挑最像的（命中率约 8/9），
  而不是报出字体的真实名称——精确识别需要字形分类模型。
  若自动匹配不理想，可在下拉框手动指定；艺术字/手写体（如 Comic Sans）会退化为最接近的常规字体。
- 极端背景（强噪声照片、文字压在复杂图案上）擦除后可能留下轻微痕迹，
  可切换擦除方式、调整字号或微调位置改善。
- **翻译文本必然出境**：识别 / 擦除 / 重绘都在本机，但译文要发到服务端，
  界面上把**实际发送的那几行文字**原样列出来，不做模糊表述。
- **图片翻译只支持中 ↔ 英**：现装 OCR 是 `ch_PP-OCRv3`（中英），
  日 / 韩 / 西里尔识别不出来，换多语言识别模型是独立的前置任务。
- **译文长度不可控**：中→英常涨 30~50%，默认开着「过长缩字号」压回原框宽，
  但缩得太狠会与原文观感差很多——不满意可改译文，或发送到「无痕改字」精修。
- 竖排文字、艺术字/手写体目前按常规横排处理。
- 服务为内存会话模式，重启后需重新上传（会话默认保留 4 小时）。
